## Findings

### Process event worth recording: the automated review pipeline failed mid-epic, and the fallback held

- **Story 4.2's four-layer review agents all failed on launch** — every one hit the account's session rate limit (`HTTP 429`, "You've hit your session limit") before producing any findings. This is not a code finding but a real process event this session lived through, and it's exactly the kind of thing `evidence-gathering.md` asks session logs to capture: what was tried and what happened when the normal path broke. Rather than skip review or fabricate a pass, the same session read the full diff manually and applied the same four lenses (missing-behavior, edge-case tracing, verification-gap, spec-conformance) by hand, sourced entirely in `spec-4-2-...md`'s own Review Triage Log — and that manual pass still found and fixed two real issues (below). This is genuine evidence the *process* (adversarial review against a diff) has value independent of *which* mechanism executes it, and that a documented manual fallback is preferable to silently shipping unreviewed when the automated path is unavailable.

### This epic's two real findings

- **Story 4.1: destination-filter isolation was asserted but never actually proven by the test suite.** The original "no listings" test only checked a destination with *zero* accommodations — a regression that dropped the `destinationId` filter entirely (returning every destination's listings for every query) would still have passed every existing test. Found by acceptance-auditor, tracing the AC text ("filtered to that Trip's destination... never the full unfiltered catalog") against what the tests actually proved rather than what they were named. Fixed with a test that seeds a second destination's own listing and asserts each destination's results contain only its own. This is a distinct, valuable class of finding from anything flagged in Epics 1–3: not "missing coverage" in the generic sense, but "the existing test's assertion doesn't actually establish the property its name claims."
- **Story 4.2 (found in the manual pass): the replace-confirm banner's appearance wasn't announced to screen readers, and its `role="alertdialog"` claimed modal semantics the implementation didn't provide** (no focus trap exists anywhere in this app). Both are accessibility-floor violations of the same EXPERIENCE.md requirement Epic 2's `BuddyToggle`/`PendingBuddyRequests` reviews already established and every subsequent same-page-update UI had correctly followed — this is the first time in 4 epics that a *new* same-page-update UI shipped *without* the announce call the project's own established convention requires, rather than a case of the convention itself being questioned. Fixed by adding the missing `announce()` call and correcting the ARIA role to `role="group"`.
