## Findings

### The one significant defect this epic shipped-then-fixed: a real concurrency bug

- **Story 2.3's accept/decline race condition** — the single most consequential finding across Epic 2, and arguably across the whole project's review history so far. `acceptBuddyRequest`/`declineBuddyRequest` originally checked `status === 'pending'` via a separate read, then wrote — a classic TOCTOU gap. All three independent review layers (blind-hunter, edge-case-hunter, verification-gap) caught it independently in the same pass, and edge-case-hunter additionally noted it was reachable from an ordinary rapid double-click, not just an adversarial concurrent request. Fixed with an atomic `updateMany({ where: { id, tripId, status: 'pending' } })` claim, verified by a real concurrent-request test. Sourced: `spec-2-3-accept-or-decline-a-buddy-request.md`'s Review Triage Log, first entry (`high, patch`). This is exactly the class of bug a single-threaded manual read of the code tends to miss — worth naming in this retrospective as the epic's clearest validation that the three-layer review process (rather than a single pass) earns its cost.

### Aggregate view: duplication map

- **`ApiError`/`throwForResponse` duplicated a third time** (`buddies/api.ts`) — continuation of the Epic 1 finding, not a new pattern. See Previous-retro follow-through above.
- **`formatDateRange` was duplicated four times before this epic's own review caught and fixed it within the same story.** Story 2.2's review found the function copy-pasted across `TripDetailPage`, `MyTripsPage`, and two new Buddies screens, and extracted it to `shared/formatDateRange.ts` in the same commit (`spec-2-2-...md` Review Triage Log). Contrast with the `ApiError` case: this duplication *did* get consolidated, on the fourth occurrence, within a single story's own review rather than needing a separate retrospective to notice it. Worth recording as a positive counter-example — the review process is capable of catching and fixing exactly this class of problem; it simply didn't happen to trip that threshold for `ApiError` within any single story's diff (each `ApiError` copy was compared only against its immediate predecessor, never against all prior copies at once).

### Aggregate view: god-file growth (watch, not fix-now)

- **`apps/api/src/features/trips/routes.test.ts` grew from 427 to 700 lines within this epic alone** (net +273, confirmed both via `git_evidence.py`'s per-file churn and directly via `git show <commit>:<path> | wc -l` at the epic's start and end commits). No single story's review flagged this — each story's own diff against the file looked like a reasonable, scoped addition (a new `describe`-style block of tests for that story's new routes). The file now hosts test coverage for itinerary, Trip-settings PATCH (from Epic 1), and buddy-request accept/decline/list (this epic) in one flat file with no internal grouping beyond top-to-bottom test order. Not a defect — every test in it passes and the file remains readable — but a trend worth naming before a future epic (4.2 also touches this same file) pushes it past a size where a single reviewer can hold the whole thing in mind.

### Pattern consistency: a lesson from Epic 1 visibly applied

- **Story 2.1's `BuddyToggle` shared-mutation-instance bug and its fix set the pattern every later story followed correctly.** The toggle and note fields originally shared one `useUpdateTripSettings` instance, coupling their `isPending` states in violation of the story's own frozen spec (`spec-2-1-...md`, first Review Triage Log entry). Once fixed (two separate instances), this became the established idiom: `spec-4-2-attach-an-accommodation-listing-to-a-trip.md`'s Code Map explicitly cites this exact precedent ("a dedicated `useUpdateTripSettings` instance, not shared with `BuddyToggle`'s two — spec-2-1 already established that a shared instance would couple independent controls' `isPending` state") and both `AccommodationsPanel` (Epic 4) and every later multi-control component followed it without re-discovering the bug. Recorded here as a genuine case of a finding becoming durable project knowledge, not just a one-off patch.
