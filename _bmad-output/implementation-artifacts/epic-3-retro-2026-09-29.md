## Findings

### The epic's standout defect: a real security vulnerability, caught before shipping

- **Story 3.1's file-extension trust bug.** `apps/api/src/shared/uploads.ts`'s original `filename()` derived the on-disk extension via `extname(file.originalname)` — fully client-controlled — while `fileFilter` only validated the (also client-controlled, but separately-spoofable) `mimetype` field. A request could pass the mimetype check with `image/png` while naming the file `evil.svg`, landing an attacker-chosen extension in a directory (`apps/api/uploads/`) served statically at `/uploads/*` — a stored-content-type mismatch with a real (if narrow) XSS angle via SVG. Found by edge-case-hunter. Fixed by deriving the extension from a `MIME_EXTENSIONS` map keyed by the already-validated `mimetype`, never from `originalname` (`spec-3-1-...md` Review Triage Log). This is the first genuine security finding (as opposed to correctness/UX) across all three epics reviewed so far, and it was caught by the same edge-case-hunter layer that also caught Epic 2's concurrency race — both times, a layer whose job is specifically to trace attacker-controlled input found the one bug in its epic that a purely functional read of the code would have missed.

### Recurring pattern: shipped diffs deviating from the story's own frozen Code Map

- **Story 3.2's missing Destination eyebrow.** The spec's own Code Map explicitly specified `eyebrow = destination name if linked` for the listing row, but the shipped `WriteupsPage` passed no `eyebrow` — and the backend's `WRITEUP_SUMMARY_SELECT` never even fetched `destination.name`/`.country` for list items, making the omission structural, not cosmetic. Found independently by blind-hunter and acceptance-auditor (`spec-3-2-...md` Review Triage Log). This is the same *shape* of finding as Epic 1's Story 1.3 chore-commit note ("every destination `Row` was rendered with neither `href` nor `onClick`... contradicting EXPERIENCE.md's 'click anywhere' contract" — later self-corrected by Story 1.3 itself) and distinct from, but related to, Epic 1's "guard added to stop new actions but not an already-open action's commit path" pattern: in both families, an implementation session correctly builds *most* of what its own plan describes and then ships with one piece of that same plan quietly missing. Three occurrences of this general shape across three different epics (1, 1 again via the chore commit, 3) suggest the acceptance-auditor lens (checking the diff against the spec's own Code Map line by line) is carrying real, repeated weight — worth continuing to run it on every story rather than treating it as a formality.
