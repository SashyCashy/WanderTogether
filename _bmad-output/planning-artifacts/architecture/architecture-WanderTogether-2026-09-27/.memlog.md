- (assumption) [ASSUMPTION] Stack choice: React 19 + Vite (SPA frontend) + Node.js/Express 5 (REST API backend) + Prisma+SQLite (persistence) — a well-known, current, zero-cloud-setup starter fitting a solo tutorial build. Chosen over Next.js full-stack because PRD/brief explicitly call this 'React-based' (a plain SPA), and over MongoDB because there's no need for schemaless flexibility and Prisma+SQLite needs no external service. Alternative considered and rejected: Next.js App Router (would fold frontend+backend into one framework, arguably less setup) — rejected because it silently answers a stack question the brief already answered (React SPA) rather than adopting it.
- (decision) [ASSUMPTION] Paradigm: Vertical Slice Architecture. Each PRD Feature (§4.1-4.5: Discovery, Group Trip Planning, Travel Buddies, Trip Write-ups, Accommodations) maps 1:1 to a backend slice (routes+service+data access) and a frontend slice (matching EXPERIENCE.md IA surfaces). Chosen over layered/hexagonal because the PRD's feature boundaries are already clean and stable, and a tutorial-scale solo build gets more value from 'find everything about X in one folder' than from enforcing port/adapter abstractions with no second implementation to swap in.
- (constraint) AD-1 [ASSUMPTION]: Slice boundary rule — a slice may read another slice's data only through that slice's exported service functions, never by querying its Prisma tables directly. Binds: all 5 feature slices. Prevents: e.g. the Buddies slice and the Trips slice both writing ad hoc SQL/Prisma calls to add a member to a Trip, diverging over time (one adds validation, the other doesn't).
- (constraint) AD-2 [ADOPTED from PRD FR-6]: Trip access is link/code-based, not session-based. Every API request touching a Trip resource carries the Trip Code (path param), and the API treats code-possession as sufficient authorization — no user/session model anywhere in the backend. Binds: Trip, TravelBuddyRequest, itinerary, accommodation-attachment endpoints. Prevents: one slice inventing a cookie/session check while another trusts a client-supplied flag, producing two incompatible access-control mechanisms.
- (constraint) AD-3 [ADOPTED from PRD §4.2/§9]: Trip Codes are generated with nanoid at 10+ characters (URL-safe alphabet), never sequential/incrementing ids, for any Trip. Binds: Trip creation. Prevents: a builder using auto-increment ids for Trips (guessable, defeats FR-6's access model) while another resource correctly uses random ids.
- (constraint) AD-4 [ASSUMPTION]: Single Prisma schema is the sole source of truth for all 6 core entities (Trip, TripMember/TravelerProfile, Destination, TravelBuddyRequest, TripWriteup, AccommodationListing) — no slice defines its own competing table or duplicated shape for a concept another slice already owns. Binds: all slices' data layer. Prevents: e.g. Buddies slice storing its own copy of 'trip member' distinct from the Trips slice's member list.
- (constraint) AD-5 [ADOPTED from PRD FR-5/EXPERIENCE.md]: Itinerary and other Trip-plan mutations are last-write-wins — a full-resource PUT/PATCH overwrite, no version/ETag/optimistic-lock check anywhere. Binds: itinerary endpoints. Prevents: one endpoint adding optimistic locking while sibling endpoints don't, producing inconsistent conflict behavior across the same Trip resource.
- (constraint) AD-6 [ASSUMPTION]: One error envelope shape for every endpoint: {"error": {"code": string, "message": string}}, non-2xx status set accordingly, validated via a single shared Zod-based error handler middleware. Binds: all API routes. Prevents: 5 independently-shaped error responses (one per slice) that the single React frontend then has to special-case.
- (constraint) AD-7 [ASSUMPTION]: All server data on the frontend is fetched/cached through TanStack Query — no slice's React components use raw useEffect+fetch+useState for server state. Binds: all 6 EXPERIENCE.md IA surfaces. Prevents: inconsistent loading/error/cache/retry behavior across surfaces (directly relevant to EXPERIENCE.md's Cold-load and Listing-failed-to-load states needing to look/behave the same everywhere).
- (constraint) AD-8 [ASSUMPTION]: Photo storage — uploaded photos (Trip Write-ups) are written to local disk (apps/api/uploads/) via multer and referenced by relative URL path in the DB; never base64-in-SQLite, never a cloud object-storage dependency. Binds: Trip Write-up photo fields. Prevents: one code path storing base64 blobs (bloats the DB file) while another assumes a cloud URL shape.
- (constraint) AD-9 [ADOPTED from PRD addendum + Non-Goals]: The Destination catalog and Accommodation dataset are populated exclusively via one Prisma seed script matching the addendum's JSON shape. No endpoint creates a Destination or AccommodationListing at runtime. Binds: Discovery slice, Accommodations slice. Prevents: an admin/create endpoint accidentally getting built for what PRD Non-Goals defines as static seed data.
- (direction) Deferred, with reason: (1) Deployment/hosting — this spine covers local development only; SQLite-as-a-file complicates typical serverless hosts, so picking a host is deferred until the tutorial needs a live URL. (2) Real-time collaboration beyond last-write-wins (AD-5) — PRD explicitly scoped out. (3) Accounts/auth — PRD Non-Goal. (4) Rate-limiting/abuse prevention on public write endpoints (buddy requests, write-ups) — PRD Open Question, no accounts to throttle against yet. (5) Real payment/booking integration — PRD Non-Goal.
- (question) Carried open from PRD (unresolved, not this spine's to answer): should itinerary support structure beyond a flat list (e.g. grouping by day)? Revisit if a future epic needs it — AD-5's last-write-wins rule and the ItineraryItem shape would need revisiting together if so.
- (constraint) AD-10 [ASSUMPTION, caught during input reconciliation against EXPERIENCE.md's My Trips surface]: With no accounts/sessions (AD-2), the backend has no concept of 'a user's trips' - every request is just 'give me Trip X by its code.' My Trips is populated entirely client-side: the frontend shared layer maintains a localStorage index of {tripCode: displayName} for every Trip this browser has created or joined (also reused to skip re-asking for a Traveler Profile on revisit), and My Trips renders by looking up each stored code via the normal per-Trip GET. Binds: my-trips frontend slice, shared frontend layer. Prevents: a builder inventing a server-side 'recent trips by IP/cookie' mechanism that contradicts AD-2's stateless, code-only access model.
