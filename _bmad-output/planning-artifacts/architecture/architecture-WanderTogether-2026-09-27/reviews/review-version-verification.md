# Version Verification Review — WanderTogether

## Overall verdict

The version *numbers* in the Stack table are trustworthy — every pinned figure (Node 24 "Krypton", React 19.3, Vite 8.3.0, Express 5.2.1, Prisma 7.10.0, TanStack Query 5.103.2, Zod 4.6.5, nanoid 6.0.1) matches what's actually current on npm/GitHub as of late September 2026, and each library still exists, is still maintained, and still fits its stated role. However, two of the picks carry **load-bearing setup requirements that changed in their latest majors and aren't reflected anywhere in the spine** (Prisma 7's mandatory SQLite driver adapter, and nanoid 6's ESM-only distribution) — if the spine is taken literally as written, a builder following it verbatim will hit a hard runtime/build error on day one. These need one added line each, not a different tech choice.

### Findings

- **high** Prisma 7's SQLite support requires an explicit driver adapter package the spine never names. Prisma ORM 7 removed the old built-in SQLite engine path; SQLite now works only through `@prisma/adapter-better-sqlite3`, wired up via `new PrismaClient({ adapter })` — the old `datasourceUrl`/`datasources` constructor options were also removed in v7. The Stack table lists "Prisma ORM (+ SQLite) 7.10.0" as if it's a single package, and AD-9/Structural Seed reference `schema.prisma`/`seed.ts` with no mention of an adapter dependency. Confirmed via Prisma's own v7 upgrade guide and SQLite connector docs (docs.prisma.io/docs/guides/upgrade-prisma-orm/v7, prisma.io/docs/orm/v7/core-concepts/supported-databases/sqlite), plus the 7.3.0 changelog noting a SQLite/better-sqlite3 version-pinning fix (prisma.io/changelog/2026-01-21). *Fix:* add `@prisma/adapter-better-sqlite3` (and `better-sqlite3` itself as its native dependency) to the Stack table alongside Prisma, and note in the shared Prisma-client-singleton description that the client is constructed with the adapter, not a bare `DATABASE_URL`.

- **high** nanoid 6.0.1 is pure ESM with no CommonJS build, and the spine doesn't state which module system `apps/api` uses. Confirmed via nanoid's own issue tracker (github.com/ai/nanoid/issues/491, #365) and the package's declared Node engines (`^22 || ^24 || >=26`, satisfied by Node 24 — that part is fine). The ESM-only distribution has been true since nanoid v4 and remains true in v6: a CommonJS Express app that does `require('nanoid')` gets `ERR_REQUIRE_ESM` and cannot work around it with a static import. AD-3 mandates nanoid for Trip Codes and the Consistency Conventions table mandates it for all entity ids, so this isn't optional or swappable-later — it determines whether `apps/api`'s `package.json` needs `"type": "module"` (or the whole slice tree needs to route ID generation through a dynamic `await import('nanoid')`). *Fix:* add one line to the spine committing `apps/api` (and ideally the whole repo) to ESM (`"type": "module"`, `.mjs`/native `import` throughout, ts-node/tsx configured for ESM) — or, if CommonJS is preferred for the Express side, swap nanoid for a CJS-compatible ID generator (e.g. `uid`, or pin to `nanoid@3.x` — accepting that this is the one place where "latest major" isn't actually the right call for a CJS backend).

- **medium** multer left unpinned ("latest stable at install time") is reasonable as a policy, but the spine should still name a floor given multer's own recent CVE history. Multer's current latest is 2.4.0; the fix for the most severe recent issue (CVE-2025-7338, a DoS via a single malformed multipart upload — GHSA-g5hg-p3ph-g8qg, ZeroPath and IBM security-bulletin writeups) landed in 2.0.2, and a second DoS (CVE-2025-48997, empty-string field name) was fixed in 2.0.1. Anything in the 1.4.4-lts.1–2.0.1 range is exploitable. multer remains the standard Express file-upload middleware (built on `busboy`, actively maintained by the expressjs org, 6700+ dependents) — no newer standard has superseded it, so keeping it is correct. *Fix:* change the Stack table entry to `multer ^2.4.0 (minimum 2.0.2 — versions <2.0.2 carry CVE-2025-7338)` instead of leaving it fully unspecified, so a lockfile drift or stale cache can't silently pull in a vulnerable pre-2.0 release.

- **low** Vite is pinned to 8.3.0, but 8.3.1 shipped since (published roughly two-and-a-half weeks after 8.3.0, right around/just after the spine's authoring date). This is a trivial patch-level drift, not a correctness issue — Vite 8's Node requirement (20.19+/22.12+) is comfortably satisfied by Node 24, and nothing in the 8.3.x patch line is behavior-changing for this stack. *Fix:* bump the pinned version to `8.3.1` (or word it as `^8.3.0` / "8.3.x") when the build actually starts, rather than re-verifying; no action needed for the spine as a planning artifact.

- **low** Prisma ORM 8 reaches general availability in October 2026 — i.e., within roughly a month of this spine being authored (2026-09-27), per Prisma's own roadmap and release-status pages (prisma.io/docs/orm/release-status, prisma.io/blog/prisma-next-roadmap). The spine's explicit choice to pin 7.10.0 stable and reject the "8.x release-candidate line" is the correct call for a build starting now — Prisma 7 keeps getting security/bug-fix support for 18 months past Prisma 8's GA, so there's no urgency to move. *Fix:* none required now; add a one-line note to "Deferred" flagging that Prisma 8 GA is imminent and worth a deliberate revisit (not a silent `npm update`) once it ships, since 8 removes/changes several features (e.g. `$extends`, some nested writes) that could affect the seed script or service layer if adopted casually later.

- **low** Ecosystem-direction check, informational only: Drizzle ORM has been closing the download gap with Prisma through 2026 and, by some reports, briefly surpassed it, partly because Prisma's pre-7 Rust query engine was a real cold-start/bundle-size liability that Prisma 7 was built to fix (multiple 2026 comparison pieces, e.g. bytebase.com/blog/drizzle-vs-prisma, techsy.io/en/blog/prisma-vs-drizzle-orm). Prisma remains the most-downloaded TypeScript ORM overall with the broadest database support, and nothing here suggests Prisma is being deprecated or is a poor fit for a tutorial-scale SQLite app. *Fix:* none — this is a "know the landscape" footnote, not a reason to switch. The Vite + React SPA / separate Express API / Prisma+SQLite / no-auth combination remains a standard, well-supported, current way to build this class of app in 2026; no bundler or ORM has supplanted it outright.

### Confirmed accurate, no fix needed
- Node.js 24.x LTS "Krypton" — correct codename, correct LTS status (nodejs.org/en/blog/release/v24.11.0, github.com/nodejs/node/releases).
- React 19.3 — released 2026-09-09, confirmed current stable (react.dev/blog/2026/09/09/react-19-3).
- Express 5.2.1 — confirmed latest on npm (published 2025-12-01); Express 5 has been npm's default/production-recommended major since v5.1.0 (March 2025), with Express 4 in maintenance-only mode (expressjs.com/en/blog/2025-03-31-v5-1-latest-release). No known Node 24 compatibility issue surfaced.
- TanStack Query 5.103.2 — confirmed latest on npm; requires React 18+ (via `useSyncExternalStore`), which React 19.3 satisfies with no caveats.
- Zod 4.6.5 — confirmed latest on npm (published ~9 days prior to spine date), no compatibility concerns found with the rest of the stack.
