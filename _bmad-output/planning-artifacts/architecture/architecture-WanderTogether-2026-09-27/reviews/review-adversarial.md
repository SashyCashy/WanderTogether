# Adversarial Incompatibility Review — WanderTogether

## Overall verdict

The spine's 10 ADs are internally consistent as stated, but several bind narrower surfaces than the slices actually need to build, and one (AD-4) governs a file that no AD says who writes first or when — both gaps let two AD-compliant builders produce genuinely incompatible systems. The most serious hole is a security/product one: nothing stops the Buddies browse listing from leaking the Trip Code itself, which would let anyone self-join a trip and skip the request/accept gate FR-8/FR-9 exist to enforce. This is not an empty-findings situation — the review surfaced ten real incompatibilities, four of them critical/high.

### Findings

- **critical** Buddies browse listing can leak the Trip Code, bypassing the request/accept approval gate entirely. **Scenario:** Builder A (buddies slice, frontend + backend) implements `GET /trips/open-to-buddies` by having `trips.listOpenToBuddies()` return full Trip rows — including `code` — reasoning that AD-2's rule ("possessing a valid code is sufficient authorization... no per-member permission levels exist") means there's nothing to hide, and AD-1 is satisfied because buddies still calls into the trips service rather than querying Prisma directly. Builder B (trips slice) assumes Trip Codes are only ever handed out by a member deliberately sharing a link (per UX flow UJ-1, "she copies the link to share elsewhere") and that the open-to-buddies listing must return an opaque trip reference (id/summary), never the code, precisely so FR-8/FR-9's request→accept flow remains the only path a stranger can gain access through. Both builders satisfy AD-1, AD-2, and AD-4 to the letter — AD-1 only governs *how* one slice reaches another's data, not *what fields* a shared service function is allowed to return, and AD-2 never distinguishes "can view a trip" from "can edit a trip," so nothing forbids the leak. If Builder A's version ships, any visitor to the Buddies tab can copy the code straight out of the listing and self-join every open trip immediately, silently defeating FR-8/FR-9's entire approval step. *Fix:* Add an AD stating that any endpoint or service function returning Trip data to a non-holder-of-the-code context (discovery/buddy-browse listings) must return a restricted view (no `code`/link field) — only per-Trip endpoints reached with the code in the path may include it.

- **critical** "Add a Trip member" has two plausible, mutually exclusive interpretations, so TripMember may or may not exist for ordinary joiners. **Scenario:** PRD's Glossary says a Traveler Profile is "not persisted across Trips or devices," which Builder A (trips slice, implementing FR-4 join-by-code) reasonably reads as: setting a display name is a client-only, ephemeral act — no `TripMember` row is created merely by opening a trip and naming yourself, since AD-2 already grants full edit rights to anyone with the code regardless of membership records. Builder B (buddies slice, implementing FR-9 accept) needs `TripMember` to be a real, queryable, persisted list — "accepting a request adds the requester as a full Trip member" only means something if TripMember rows exist and are checked somewhere (e.g., to gate who can Accept/Decline per FR-9: "any member of the target Trip"). Both builders are fully AD-1/AD-4-compliant (buddies calls `trips.addMember()`, never touches the table directly), yet the resulting system has TripMember populated only for buddy-accepted joins and never for direct-link joiners — so "any member of the target Trip can accept or decline" (FR-9) has no members to check against for a trip nobody joined via a buddy request, and itinerary/attendee displays are incomplete. *Fix:* A tightened AD-4 (or a new AD) must state explicitly whether opening a Trip and setting a Traveler Profile always creates/upserts a persisted TripMember row, and must name the single service function (signature and idempotency rule) both the direct-join and buddy-accept paths call.

- **high** No AD assigns authorship or sequencing for the first `schema.prisma`, so AD-4 can't prevent shape collisions before the file exists. **Scenario:** Builder A (write-ups slice) and Builder B (some other slice, or a second builder working the same slice on a different day) both need to add fields for FR-10's "one or more photos" to `TripWriteup` before a canonical schema exists. AD-4's list of owned entities names `TripWriteup` but not a `Photo` entity, and AD-8 only says photos are "referenced by relative URL path in the DB" — singular, ambiguous on cardinality. Builder A stores `photoUrls: Json` (a stringified array) directly on the `TripWriteup` row — no new entity, trivially "AD-4 compliant" (still one schema, no duplicate ownership of a named entity). Builder B instead adds a new `Photo` model with a `TripWriteup` relation — also AD-4 compliant, since AD-4 never says new entities can't be introduced, only that named entities can't be duplicated. Both are correct per the letter of AD-4, yet the API response shape (`photoUrls: string[]` vs `photos: {id, url}[]`) is incompatible for any frontend consumer. This is a symptom of a broader gap: AD-4 is an ownership rule, not a process rule — nothing says who authors the first complete schema.prisma, when, or how a slice proposes a field addition against entities it doesn't own. *Fix:* Add an AD naming schema.prisma as a first-class artifact authored (or reviewed) in one place before slice implementation starts, with a rule that new fields/entities touching another slice's model require an explicit schema PR reviewed against all consuming slices — not independent invention.

- **high** AD-5's last-write-wins rule is scoped to "itinerary endpoints," leaving Trip-level fields like `openToBuddies` and `attachedAccommodationId` with no stated mutation strategy, inviting a full-overwrite endpoint that clobbers them. **Scenario:** Builder A (trips slice backend) extends AD-5's precedent ("itinerary writes are full-resource overwrites with no version/lock check") to the whole `Trip` resource for consistency, implementing a single `PUT /trips/:code` that accepts and overwrites the entire Trip document — a defensible reading since AD-5 establishes overwrite-without-locking as the slice's house style and no AD says otherwise for non-itinerary fields. Builder B (trip-detail frontend, building the open-to-buddies toggle per EXPERIENCE.md's Component Patterns) sends a minimal partial body `{openToBuddies: true, note: "..."}` to that same endpoint, assuming (reasonably, since AD-5 explicitly says its rule binds only "itinerary endpoints") that non-itinerary fields get ordinary partial-update semantics. The result: toggling open-to-buddies silently nulls out itinerary items and the attached accommodation, because Builder A's full-overwrite endpoint treats missing fields in the request body as "set to empty." Both builders followed AD-5 to the letter — one by extension, one by strict scope-reading — and produced a data-loss bug neither slice's builder would catch in isolation. *Fix:* Add an AD explicitly stating the mutation strategy (PATCH-partial vs PUT-full-overwrite) for every non-itinerary Trip field, separately from AD-5.

- **high** AD-6's error envelope doesn't address multer's own error path, so upload failures can diverge in `code` semantics from the rest of the API. **Scenario:** Builder A (shared `error-middleware` author) writes the one shared handler assuming all thrown errors are either a `ZodError` or a custom `AppError` with an explicit `code`, mapping anything else to a generic `{code: "INTERNAL_ERROR"}`. Builder B (write-ups slice) wires `multer` (`upload.array('photos')`) directly onto the publish route per AD-8; when a file exceeds the size limit or has the wrong mimetype, multer throws a `MulterError` with its own `.code` (e.g. `LIMIT_FILE_SIZE`) before any Zod validation runs. Neither builder violated AD-6 — the shared handler still produces the one envelope shape, and write-ups never assembled an error response ad hoc — but because no AD or convention says the shared handler must special-case `MulterError` into a domain-meaningful `code`, every upload failure surfaces as `INTERNAL_ERROR` while every other validation failure surfaces as a specific Zod-derived code, so the frontend's shared error-handling logic (built to branch on `code`, per AD-7's single-data-layer intent) cannot treat "file too large" specially even though the envelope shape is technically uniform. *Fix:* Extend AD-6 (or add a new AD) to require the shared error middleware to explicitly translate known middleware-level errors (MulterError codes, at minimum) into the same `code` vocabulary used elsewhere, and to specify multer's position in the middleware chain relative to Zod validation.

- **medium-high** AD-10 doesn't specify the trigger condition for writing to the "My Trips" localStorage index, so slices disagree on what counts as "created or joined." **Scenario:** Builder A (trip-detail slice) writes to the shared localStorage index on every successful `GET /trips/:code` — including a plain view of a trip reached via a shared link that the visitor never explicitly "joined" — reading AD-10's phrase "every Trip this browser has created or joined" loosely as "every Trip this browser has ever opened." Builder B (buddies slice) only calls the shared write function at the moment a Travel Buddy Request is accepted, treating "joined" narrowly as "granted membership," and never writes an entry for someone who merely viewed a trip via a link without setting a Traveler Profile. Both are AD-10-compliant (one shared `localStorage` index, `{tripCode: displayName}` shape, used to render My Trips and skip re-asking for a profile) — yet the resulting My Trips list is either polluted with trips the visitor never actually joined (Builder A's reading) or missing trips they legitimately gained access to via buddy-accept (Builder B's reading), depending on which slice's flow the visitor went through first. *Fix:* Tighten AD-10 to name the exact trigger (e.g., "on Trip creation, and on first successful Traveler Profile submission for a code — never on a bare GET") as a single call site both flows must invoke.

- **medium-high** No Trip lifecycle/expiry policy exists anywhere, so AD-10's assumption that codes remain valid indefinitely is unstated and could be silently broken. **Scenario:** Builder A (trips slice) adds a cleanup job or TTL (e.g., pruning trips inactive for N months, reasonable for a SQLite-file tutorial app that will otherwise grow unbounded) — nothing in any AD forbids this; AD-2 only governs *access method* (code vs session), not *retention*. Builder B (my-trips slice) builds strictly against EXPERIENCE.md's defined states, none of which include "a My Trips row whose Trip Code no longer resolves" — only "Invalid/expired Trip Code" on the *Join a Trip* surface is defined, not an equivalent for a stale row already sitting in My Trips. Both builders are fully AD-compliant, yet once Builder A's cleanup runs, Builder B's My Trips rows for pruned trips have no defined behavior (crash, silent disappearance, or a broken row are all "correct" by omission). *Fix:* Add an AD (or amend AD-10) stating Trips are retained indefinitely with no expiry in v1, and specify the My Trips UI's handling of a `404` on a stored code as an explicit state, matching the rigor EXPERIENCE.md already gives the Join-a-Trip failure case.

- **medium-high** AD-7 mandates TanStack Query everywhere but establishes no shared query-key convention, so two slices can cache the same Trip under different keys and diverge after a write. **Scenario:** Builder A (trip-detail slice) defines the query key for a full trip fetch as `['trip', tripCode]`, returning the full payload (itinerary, members, accommodation). Builder B (my-trips slice), wanting a lighter per-row fetch for a list of N trips, defines a separate lower-payload query under `['trips-summary', tripCode]` hitting the same or a similar endpoint. Both slices satisfy AD-7 to the letter — "every server-data fetch/mutation goes through TanStack Query," full stop — but because the query-key namespaces never overlap, a mutation on trip-detail (e.g., renaming the Trip) invalidates only `['trip', tripCode]`; My Trips' `['trips-summary', tripCode]` entry is untouched and shows the stale name until an unrelated refetch. This directly undermines EXPERIENCE.md's requirement that Cold-load/Listing-failed states "look and behave the same everywhere" — the underlying cache coherency across surfaces is exactly what AD-7 was meant to guarantee but doesn't name a mechanism for. *Fix:* Add a query-key convention to Consistency Conventions (e.g., "all Trip reads key off `['trip', tripCode]`; slices needing a subset select from that cached object rather than defining a parallel key") so cross-slice invalidation is automatic.

- **medium** The Consistency Conventions' id-format rule is ambiguous between two different ID schemes for non-Trip entities. **Scenario:** The table says: "Ids: `nanoid` strings everywhere (never auto-increment) — Trip Codes at 10+ chars per AD-3, all other entity ids at the library default." Builder A (discovery slice, authoring `Destination`/`AccommodationListing` ids) reads "the library default" as *Prisma's* own default id generator (i.e., `@default(cuid())`), treating "nanoid strings everywhere" as describing only the Trip Code family. Builder B (buddies/write-ups slice, authoring `TripMember`/`TravelBuddyRequest`/`TripWriteup` ids) reads the same sentence as "everywhere" governing, with "the library default" meaning *nanoid's* own default length (21 chars) as opposed to AD-3's explicit 10-char minimum for Trip Codes specifically. Both readings are defensible parses of the same sentence, and each builder can point to the literal text to justify a different generator (`cuid()` vs `nanoid()`) for entities the other never touches — so the schema ends up with two incompatible id formats for otherwise-identical-looking string PKs, purely from parsing the same convention sentence two ways. *Fix:* Rewrite the sentence unambiguously: name the exact generator call (e.g., `nanoid()` with no arguments, for every entity id in the schema, full stop) and remove "library default" as a phrase.

- **low-medium** "One request per person per Trip" (buddy request pattern) has no server-enforceable identity to key on, and no AD says how it's enforced, so builders can implement incompatible half-measures. **Scenario:** EXPERIENCE.md's Buddy request row pattern states "one request per person per Trip," but with no accounts and no session model (AD-2's whole premise), there is no stable identifier for "a person." Builder A (buddies slice frontend) enforces this client-side only — a localStorage flag set after a successful submit, hiding the form on return visits from the same browser — trivially bypassed by a private window, but fully compliant with every stated AD (none of which mandate server-side uniqueness). Builder B (buddies slice backend), independently, adds a Prisma `@@unique([tripId, requesterName])` constraint on `TravelBuddyRequest`, enforcing uniqueness by display name — which both silently blocks a legitimate second request from someone who mistyped their name the first time, and does nothing to stop a determined duplicate (just retype the name). Neither builder violated an AD; the two mechanisms (client flag vs DB constraint) can also both ship at once and disagree — the DB rejects a resubmission the client-side flag had already permitted (e.g., after clearing localStorage), surfacing as an unexplained save failure per EXPERIENCE.md's generic "Didn't save. Try again." message, which was designed for form failures, not policy conflicts. *Fix:* Add an AD (or explicitly a Non-Goal note) stating this constraint is not server-enforced in v1 — client-side-only, best-effort — so no builder invents a DB-level uniqueness rule that silently conflicts with it.
