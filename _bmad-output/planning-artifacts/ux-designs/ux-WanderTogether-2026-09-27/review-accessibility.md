# Accessibility Review — WanderTogether

## Overall verdict

For a hobby/portfolio project this spine is unusually disciplined about accessibility on paper — it names a concrete focus treatment, requires `aria-describedby` for inline errors, sets a 44px touch-target floor for rows, and already requires alt text on photos with swatches excluded (so that boilerplate check is genuinely satisfied, not flagged below). The real problems are (1) a hard color-contrast failure in the sage accent color used for eyebrow labels and status tags — used on nearly every screen — and (2) a handful of interaction patterns (hover-only row actions, the toggle switch, the mobile nav collapse) that are described visually/behaviorally but never given the ARIA semantics or keyboard-equivalent needed to actually meet the "Tab/Enter/Space" floor the doc itself sets. None of this requires a rewrite; it's a punch-list a reviewer would reasonably send back before calling the spine "AA."

### Findings

- **critical** Sage accent color fails contrast everywhere it's used as text (`DESIGN.md` colors frontmatter; `DESIGN.md.Typography` eyebrow; `DESIGN.md.Components` tags/badges). `accent: #7C9885` on `background: #F7F6F2` computes to ≈2.9:1, and on `surface: #FFFFFF` ≈3.1:1 — both well under the 4.5:1 AA requirement for normal text (the eyebrow is 12px/700 and tags are label-sized, neither qualifies as "large text," so 3:1 doesn't apply either). This isn't a decorative accent — it's the literal color of the "Plan together" / "Trip" eyebrow labels on both mockups and of the "open to buddies" and "Attached" status tags, i.e. the one place the product communicates real state (a trip is open to buddies, a listing is attached) using color+text. `EXPERIENCE.md.Accessibility Floor` explicitly says "navy-on-cream and navy-on-white both verified at WCAG AA" — notice it does not claim sage was verified, and it wasn't; it fails. *Fix:* darken the accent to roughly `#5C7A67`–`#4E6B58` (still read as sage, ≥4.5:1 on both cream and white) for any place it's used as text, or keep the current sage strictly for non-text decoration (borders, the toggle's own fill) and use `ink` for the actual eyebrow/tag text.

- **high** Secondary/metadata text color fails AA by a narrow but real margin (`DESIGN.md` colors frontmatter `ink-soft: #6C7A85`; used throughout row descriptions, `right`/meta text, itinerary day labels, request messages, trip meta). Computed contrast is ≈4.08:1 on `background` and ≈4.41:1 on `surface` — both below the 4.5:1 required for normal-size text (this is 13–13.5px body/caption text, not large text). It's a near-miss, but it's the color used for nearly every piece of secondary copy in both mockups (destination descriptions, "4.6 · 128 write-ups", itinerary day labels, buddy request messages, trip dates). *Fix:* darken to roughly `#5C6B76` or darker, which clears 4.5:1 on both surfaces while staying visually "soft."

- **high** Hover-revealed row actions have a stated touch fallback but no stated keyboard fallback (`EXPERIENCE.md.Interaction Primitives`: "Hover reveals secondary row actions (e.g., 'Remove' on an itinerary line) on pointer devices; touch surfaces these actions via a persistent icon instead of hover."). The doc covers mouse and touch explicitly but never says how a sighted keyboard-only user (e.g., a motor-impairment user tabbing through the itinerary) reveals or reaches "Remove" — `Accessibility Floor`'s generic "every interactive element... reachable via Tab/Enter/Space" doesn't resolve this, because the action is never described as gaining visibility on focus, only on hover/touch. As written, this is a WCAG 2.1.1 (Keyboard) / 1.4.13 (Content on Hover or Focus) gap for the one row type with an inline secondary action. *Fix:* add one line to Interaction Primitives or Accessibility Floor: "on keyboard focus, secondary row actions become visible identically to the touch treatment (persistent icon), not just on hover."

- **medium** Mobile nav collapse has no specified accessible name or state (`EXPERIENCE.md.Responsive & Platform`, `< 768px`: "Top nav collapses to a simple menu (label + icon, no persistent tab bar)."). Nothing in the spine says this control needs an accessible name (e.g. "Menu"), `aria-expanded` to communicate open/closed state, or focus management when the menu opens — a real risk given the mockup itself renders nav items as bare `<span>`s with no button semantics at all. *Fix:* one line specifying the trigger is a real `<button>` with a visible or `aria-label`d name and `aria-expanded`, and that opening it moves focus into the menu.

- **medium** Toggle switch has no stated ARIA semantics and the mockup renders it below the WCAG 2.2 minimum target size (`EXPERIENCE.md.Component Patterns`, open-to-buddies toggle; `mockups/trip-detail.html` `.switch{width:38px;height:20px;...}`). The Accessibility Floor's generic Tab/Enter/Space statement doesn't address that a toggle needs `role="switch"`/native checkbox semantics, `aria-checked`, and a programmatically associated name (the mockup just places adjacent text next to a bare `<div>`, with no `<label>` or `for`/`aria-labelledby` link) — this is the one true two-state control in the product and it's the least specified interactive element in the spine. Separately, 20px height is under SC 2.5.8's 24×24 CSS px minimum target size, and it doesn't qualify for the inline/spacing exceptions. *Fix:* specify the toggle as a native checkbox styled as a switch (or `role="switch"` + `aria-checked` + `aria-label`/associated `<label>`), and bump the hit area to at least 24×24px (visual track can stay slim if the clickable/tappable box is padded out).

- **medium** Contradictory focus treatment for inputs between the two docs, and the DESIGN.md version is inert as specified (`DESIGN.md.Components`: "Inputs: ... Focus state darkens the border, no glow." vs. `EXPERIENCE.md.Accessibility Floor`: "Focus state is a solid 2px `colors.ink` outline... not the soft glow explicitly rejected in `DESIGN.md.Components`"). These describe two different focus treatments for the same element type, and DESIGN.md's is actually unachievable as written: the input's resting border color (`border-strong`, `#23303B`) is already identical to `ink`, so there is no darker shade left for focus to "darken" *to* — a literal implementation of the DESIGN.md line would be visually imperceptible. *Fix:* delete the "darkens the border" line from DESIGN.md.Components (or explicitly say EXPERIENCE.md's 2px outline supersedes it for inputs) so there's one focus spec, not two.

- **medium** No status-message/live-region behavior specified for in-page state changes a screen-reader user can't otherwise perceive (`EXPERIENCE.md.State Patterns`: buddy request pending/accepted, Key Flow UJ-3 step 4 "a member sees the pending request... and clicks Accept"). When a trip member clicks Accept, the request presumably disappears from the pending list in place (no page reload implied) — that's a dynamic content change with no stated `aria-live` announcement, so a screen-reader user gets no confirmation the action succeeded, unlike a sighted user who sees the row vanish. Same gap applies to the note field that appears when the open-to-buddies toggle is switched on. (Note: the *declined* state and "no notification mechanism in v1" called out in State Patterns is explicitly an accepted product-level gap that affects sighted and non-sighted users equally — that one is not an accessibility-specific finding, just a general limitation worth leaving as-is for v1.) *Fix:* one line noting that in-page updates resulting from a same-page action (Accept, toggle-reveal) are announced via a polite live region, satisfying WCAG 4.1.3 Status Messages.

- **medium** Form fields appear to rely on placeholder-only labeling with no persistent visible label specified anywhere in the spine (`mockups/discover.html`: `<input placeholder="Search destinations"/>`; `EXPERIENCE.md.Component Patterns`, Trip Code entry: "Single text field + submit" with no mention of a label). Placeholder-only inputs are a common real failure mode: the hint disappears the moment the user starts typing, which is a problem for users with short-term memory/cognitive load issues and is generally discouraged practice under 3.3.2 (Labels or Instructions), even where an accessible name is technically present. *Fix:* one line in Component Patterns requiring a persistent visible label (can be visually subtle, e.g. small caption above the field) for Trip Code entry and Discover search, not placeholder-only.

- **low** Mockups model several interactive controls with non-semantic markup, with no caveat steering implementers back to the Accessibility Floor (`mockups/discover.html` nav items as `<span class="active">`/`<span>`; `mockups/trip-detail.html` `.itin-add` "+ Add a line" as plain text, `.switch` as a bare `<div>`). `EXPERIENCE.md` correctly says "Spine wins on conflict" for composition, but a developer skimming the HTML for markup structure (not just visual layout) could copy these non-interactive elements verbatim. *Fix:* a one-line note near the mockup reference ("mockups show visual composition only; interactive elements must use real button/link/input semantics per Accessibility Floor regardless of the markup shown") would close this off cheaply.

- **low** No heading/landmark structure specified for either surface (neither file states whether nav is a `<nav>` landmark, whether Discover's hero `<h1>` and Trip detail's `<h1>` coexist correctly on a page that also has a top-level "WanderTogether" logo, or what the heading hierarchy looks like across sections). Minor for a project at this stage, but a real AA audit would still note it since screen-reader users navigate primarily via headings/landmarks. *Fix:* not urgent; worth one sentence in Accessibility Floor if this doc gets a revision pass.
